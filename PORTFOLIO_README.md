#### 2. 🧠 DriftGuard — ML Network Intrusion Detection System

[![Repo](https://img.shields.io/badge/Repo-DriftGuard-blue?style=flat-square&logo=github)](https://github.com/NITHINKR06/DriftGuard) · `Jupyter Notebook 86.4%` · `Python 8.0%`

DriftGuard is a machine learning-based network intrusion detection system (NIDS) that addresses one of the most persistent challenges in cybersecurity: the inability of ML models to generalize across different network environments. Most intrusion detection systems fail when deployed in networks different from where they were trained, but DriftGuard maintains robust performance across diverse environments — from academic networks to real-world ISP traffic — without requiring retraining.

The system employs an ensemble of three complementary AI models working together through a weighted fusion approach. The Isolation Forest provides fast, unsupervised tree-based anomaly detection on high-dimensional network traffic data with a contamination factor of 0.1. The Dense Autoencoder uses a symmetric architecture (77 → 50 → 25 → 50 → 77) trained exclusively on benign traffic samples, detecting anomalies through reconstruction error analysis. The Bidirectional LSTM Autoencoder captures temporal dependencies in network flows using a window size of 10 timesteps, identifying sequential attack patterns that point-based models miss. Risk scores are computed via weighted ensemble fusion (0.3 × Isolation Forest + 0.4 × Autoencoder + 0.3 × LSTM), and SHAP (SHapley Additive exPlanations) analysis provides interpretable explanations for each flagged flow.

DriftGuard validates its approach across three distinct datasets: CICIDS2017 for training, UNSW-NB15 for cross-dataset validation, and UGR16v2noIRC for real-world ISP traffic validation. The system achieves a processing throughput of approximately 2,380 network flows per second with low latency, making it viable for production deployment. Future enhancements include Zeek real-time inference integration and automated MITRE ATT&CK technique mapping.

#### 3. 🔐 CHC Secure File Management System

[![Repo](https://img.shields.io/badge/Repo-chc--secure--file--system-blue?style=flat-square&logo=github)](https://github.com/NITHINKR06/chc-secure-file-system) · `Python 47.2%` · `TypeScript 45.2%`

The CHC Secure File Management System is a blockchain-integrated file encryption platform built around a custom cryptographic algorithm called the Contextual Hash Chain (CHC). Unlike traditional encryption approaches where a single key protects all files, CHC derives a unique encryption seed for each file by combining the user's master secret with blockchain context — specifically the latest block hash, timestamp, and file identifier — through HMAC-SHA256. This contextual derivation means that even if a single file's encryption is compromised, no other files are affected, providing forward security by design.

The encryption itself operates as a chained block cipher: each block's encryption state depends on the previous block's ciphertext through SHA-256 hash chaining, creating a sequential dependency that prevents partial file tampering. The system expands the 256-bit key state into a variable-length keystream using counter-mode SHA-256 blocks, then XORs the plaintext to produce ciphertext. For multi-user access control, the system wraps each file's encryption seed individually for each authorized user using their personal key, enabling cryptographic per-user access management without exposing the master seed.

An immutable blockchain audit trail records all file operations — uploads, downloads, access grants, and revocations — as SHA-256-chained blocks, creating a tamper-proof log that can be independently verified. The frontend is built with TypeScript and the encryption core is implemented in Python, with encrypted files stored off-chain on Firestore while metadata, wrapped keys, and blockchain records are maintained separately. This separation of concerns ensures that the encryption layer, storage layer, and audit layer operate independently, making the system resilient to single points of failure.

<summary>💻 <b>Code Snippet — CHC Encryption Core (Python)</b></summary>

```python
import hashlib, hmac

class CHCEncryptor:
    """Contextual Hash Chain encryption with forward security."""
    
    def __init__(self, master_secret: str):
        self.master_secret = master_secret.encode()
    
    def derive_seed(self, block_hash: str, timestamp: str, file_id: str) -> bytes:
        """Derive unique encryption seed from blockchain context."""
        context = f"{block_hash}:{timestamp}:{file_id}".encode()
        return hmac.new(self.master_secret, context, hashlib.sha256).digest()
    
    def encrypt_block(self, plaintext: bytes, seed: bytes, prev_cipher: bytes = b'') -> bytes:
        """CHC block encryption — each block depends on previous ciphertext."""
        chain_state = hashlib.sha256(seed + prev_cipher).digest()
        keystream = self._expand_key(chain_state, len(plaintext))
        return bytes(p ^ k for p, k in zip(plaintext, keystream))
```

#### 5. 🎮 Real-Time Cyber Defense Game

The Real-Time Cyber Defense Game is a Python Pygame project that bridges the gap between cybersecurity simulation and actual system-level firewall management. Unlike purely visual simulations, this game integrates directly with the Linux iptables firewall to apply real network security rules during gameplay. When a player identifies and clicks on a hostile (red) network packet, the game not only removes it from the screen but simultaneously executes a subprocess call to add an `iptables -A INPUT -s <IP> -j DROP` rule, genuinely blocking that IP address at the kernel level. Safe (blue) packets must be allowed through to maintain network functionality.

The game features a health system where the network's core health decreases whenever hostile packets successfully breach the player's defenses, creating urgency and real consequences for missed threats. Packets spawn with randomized IP addresses, speeds (1.5–4.0 units), and threat classifications, requiring quick visual identification and response. The rendering includes a glow effect around each packet for visual distinction — hostile packets glow red while safe packets glow blue. import * as THREE from 'three';

function createParticleSystem(scene: THREE.Scene): THREE.Points {
  const count = 5000;
  const positions = new Float32Array(count * 3);
  const colors = new Float32Array(count * 3);

  for (let i = 0; i < count; i++) {
    const r = Math.random() * 50;
    const theta = Math.random() * Math.PI * 2;
    const phi = Math.acos(2 * Math.random() - 1);
    positions[i * 3]     = r * Math.sin(phi) * Math.cos(theta);
    positions[i * 3 + 1] = r * Math.sin(phi) * Math.sin(theta);
    positions[i * 3 + 2] = r * Math.cos(phi);
    const t = i / count;
    colors[i * 3] = t; colors[i * 3 + 1] = 1.0 - t * 0.5; colors[i * 3 + 2] = 1.0;
  }

  const geo = new THREE.BufferGeometry();
  geo.setAttribute('position', new THREE.BufferAttribute(positions, 3));
  geo.setAttribute('color', new THREE.BufferAttribute(colors, 3));
  const mat = new THREE.PointsMaterial({
    size: 0.15, vertexColors: true, transparent: true, opacity: 0.8,
    blending: THREE.AdditiveBlending,
  });
  return new THREE.Points(geo, mat);
}
